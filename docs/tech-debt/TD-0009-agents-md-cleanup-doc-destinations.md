# TD-0009: agents-md-cleanup's known limits: doc destinations, the `references` seed, test detection, over-limit re-dispatch and splits, unrecorded over-limit files, scanner edge cases, test gaps, the `(whole)` exemption and the `_docs` cap

## Problem

- **The doc page a reviewer picks rests on heading titles and its own reading.** `docs` in [`agents_md_inventory.py`](../../plugins/maintenance/skills/agents-md-cleanup/scripts/agents_md_inventory.py) lists each page's headings, and the reviewer chooses a page and heading from those titles. Nothing checks that a chosen heading is the best fit, only that the target exists or is a new file under the docs folder.
- **`references` for the root AGENTS.md is a seed only.** Its path matches every mention of any AGENTS.md, so the hits are broad and not specific to the rule being moved. [SKILL.md](../../plugins/maintenance/skills/agents-md-cleanup/SKILL.md) step 4 relies on a grep for each moved rule's backticked names to find what really points at it.
- **The test's "can't run" outcome is read from the output.** Step 7 treats the size test as unable to run when its command is not found on PATH, or it exits non-zero with build or toolchain errors before reporting any test result. Telling such an error from a failing test rests on the main agent reading the output, and the filter idioms step 7 names (`dotnet test --filter`, a `pytest` path, a `jest` path, `go test -run`) are examples, so an unfamiliar runner's output can be misread either way.
- **A re-dispatched reviewer can only judge the file's own blocks.** When an over-limit target is re-dispatched on its merged text (step 4, *Size accounting*), verdicts attach to block ids of the file on disk. Incoming rules have no block ids, so the reviewer can only name them in its summary, and each becomes a question.
- **An over-limit keep that the user answers "split it" is never checked.** `_guard_length` in `agents_md_inventory.py` turns the keep into an `ask` with no `proposed`, because only the user can choose the split. The main agent then authors the parts itself, and that text never passes `check-verdicts`, so nothing confirms each part is under the word limit or that no clause is lost.
- **A file the user accepts over its byte limit is recorded only in the test's exception list.** With no test, nothing records the choice, and the next run asks again.
- **The word-count scanner has untested edge cases and two known miscounts.** These cases have no test: a fence closed by a longer fence, a tilde fence closed by backticks, and an unterminated fence or comment. `measure_rules` in [`agents_md_limits.py`](../../plugins/maintenance/skills/agents-md-cleanup/scripts/agents_md_limits.py) also counts an indented code block as a rule, and counts a loose list item's second paragraph as a rule of its own rather than part of the item. A multi-line HTML comment that opens mid-line (`- rule <!-- note\n  hidden -->`) is counted as rule text, since only a line-start `<!--` enters comment state. `_references` in [`agents_md_inventory.py`](../../plugins/maintenance/skills/agents-md-cleanup/scripts/agents_md_inventory.py) reports a made-up path for a tracked file whose name holds a newline, because `git grep -z` leaves the name unquoted and the record is split at the newline.
- **Some size paths have no test.** The `--file-bytes` and `--root-bytes` flags are tested only together with `--rule-words`, never alone, and no test pins the message for `--rule-words 0`. The inventory's `references` and `docs` lack edge tests: the 200-character text cut and a path that starts with `-`. In `test_agents_md_verdicts.py`, `WordLimitGuardTest.check_limited` duplicates `VerdictsTestCase.check` with one extra flag. `test_size_case_files` in `test_agents_md_eval.py` checks the size eval cases' files exist but does not pin the new graders' front matter.
- **A `(whole)` ruling lifts the word cap on any `fix`, `trim` or `move` text.** `_check_text_limits` skips the cap on the `new_text` (or the carried blocks) of a `fix`, `trim` or `move` whose `ruling` holds `(whole)`, top-level or in an ask's `proposed`. It does not check that the new text is still the rule the user kept whole, so a fix that also adds clauses passes uncapped. `check-verdicts` honours `(whole)` only when a line of the rulings file holds the ruling (quote marks, spacing and case aside), but it does not check that the ruling's quote is this block's, so a reviewer that copies another keep's `(whole)` ruling from the file onto a different over-limit rule still lifts the cap.
- **One eval statement overlaps another.** In the `agents-md-cleanup-size-review` eval case, statement 7's long payment-retry bullet repeats statement 5's `MAX_ATTEMPTS` rule, so a run may route that rule through either one, and the graders must accept both. That makes the case prone to flaky grading.
- **`_docs` parses every page before it applies the 200-page cap.** When both `Docs` and `docs` exist on a case-sensitive filesystem, it picks one without saying so.

## Why it exists

The destination choice is judgement work, and the reviewer sees the same titles a person would. A stricter check needs a measure of fit that nobody has defined. The `references` seed is cheap and errs toward more hits; narrowing it for the root file needs the moved rule's names, which only the skill knows. The "can't run" outcome is read from the test command's output (not found on PATH, or build or toolchain errors before any result), and the filter idioms the skill names are examples, so a framework with another idiom may run its whole suite or be judged unrunnable. The re-dispatch reuses the existing verdict shape rather than adding a new one for text that isn't on disk. Recording an accepted file needs somewhere to put it, and the exception list was the only place that already existed. Leaving `proposed` off the over-limit ask keeps the split a user decision, and the check for a user-authored split was left for later. The scanner's common cases are tested and the rest were judged rare; a mid-line comment opener was left as text so that an inline `<!--` in backticks cannot hide the rest of the file, and a newline in a file name was judged rarer than the crash its fix removed; telling an indented code block or a loose item's paragraph apart needs list-context tracking the scanner doesn't have. The missing tests and the duplicated helper were found in the final review and left for a follow-up. Telling "the same rule, corrected" from "a longer rule" needs a measure of sameness nobody has defined; the user sees the new text in the approval message. The eval overlap mirrors a real file, where rules do repeat. The `_docs` cap bounds the output, not the work.

## Impact

Low. A reviewer can pick a weaker page or heading, and the user sees it in the approval message. The root file's reference list can be noisy. A test for a framework whose filter idiom the skill doesn't name may run the whole suite or be left for the user to run. Incoming rules to an over-limit file cost one question each. A user-chosen split can leave a part over the word limit or drop a clause unnoticed until the size test runs, if there is one. A user who accepts a file over its limit without a test is asked again on every run. A scanner edge case miscounts words or bytes for an unusual document, and an indented code block or a loose item's paragraph can be reported as a rule over the limit. A comment opened mid-line can push a rule over the limit, and a newline-named file can add one bogus reference hit. An untested path can regress unnoticed. A fix of a rule kept whole can grow it past the limit, caught only by the size test's exception list. The overlapping eval statement can fail a correct run. A very large docs folder is slow to inventory, and the `Docs` and `docs` choice can surprise on a case-sensitive filesystem.

## Proposed fix

- Show the reviewer each candidate page's first lines as well as its headings, or add a check that flags a chosen heading when another heading shares more words with the rule.
- For the root AGENTS.md, have the skill pass each moved rule's backticked names to `references` as extra patterns, so the seed is replaced by specific hits.
- Read the framework from the repo's own test command (a CI step or `package.json` script) and take its filter idiom from a table in the script, with a fallback that runs the whole file's tests.
- Let the re-dispatched reviewer return verdicts for incoming rules under ids the skill assigns to them (for example `in-<n>`), and have `check-verdicts` accept them.
- Have the main agent write a user-chosen split as a `split` verdict for the ask's blocks and run `check-verdicts` on it before the approval message is re-shown.
- Record an accepted over-limit file in the guidelines section, for example as a `Size exceptions:` line, so it holds without a test.
- Add scanner tests in `plugins/maintenance/tests/` for each edge case listed above, and fix whatever they show. Track list context in `measure_rules` so an indented code block counts nothing and a loose item's later paragraphs join the item. Enter comment state for an unclosed `<!--` left after stripping complete spans when it is outside a backtick span. In `_references`, keep only hits whose path is a tracked file.
- Add tests for `--file-bytes` and `--root-bytes` alone, the `--rule-words 0` message, and the 200-character cut and a `-`-leading path. Fold `check_limited` into `check` with an `extra` argument. Pin the size graders' front matter in `test_size_case_files`.
- For a `(whole)` `fix` or `trim`, cap the new text at the longer of the word limit and the original rule's words. Also require the ruling's quote, without the token and with any `...` as a gap, to appear in the covered block's text.
- Drop the `MAX_ATTEMPTS` clause from statement 7 in the `agents-md-cleanup-size-review` fixture, or make it differ from statement 5.
- In `_docs`, stop at 200 pages before parsing, and report both folders when `Docs` and `docs` exist.

## Trigger

A user report of a poorly chosen doc page, an unchecked split, a noisy root reference list, a test left uncommitted for a framework the skill doesn't know, a repeated over-limit question, or a miscounted document. Also the next change to `docs`, `references`, the word-count scanner, `_guard_length`, the size eval cases or step 7.
