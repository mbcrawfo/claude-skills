# Event handling

SKILL.md's wake loop says what every turn does, and its verdict rule how to read a `verdict` line. Take the first row that matches.

**On every user message,** before anything else: run `run.py status <run>` and act on each line under "needs the manager", and file any open question in `notes.md` that has no item (owner-queue.md, Older runs). Then handle the message; one that does not answer or discuss the current item ends with it (owner-queue.md, AFK return). Where a unit has a title, `status` shows it in brackets after the name; commands take the bare name.
- `request <unit> <sha> <branch> unanswered since …`: handle it as `REQUEST`.
- `forward due <unit> <ids>`: forward as owner-queue.md says.
- `hold <unit>: <reason> since …`: nothing to do. A reason that starts with `answer sent:` waits on the child: show it in the tracker as `<unit> held until it asks again`. One that starts with `own session:` is on the tracker's `Elsewhere:` line; any other waits on a blocking item, which `Waiting on you:` covers.
- `<unit> PR #<pr> ready since …`: run `run.py check <run> <unit>`; on `READY <pr> <sha>`, handle it as `READY`.
- `integration push landed: run synced <unit> <sha>` (integration mode): the watcher saw the push land but `synced` never ran. Run `run.py synced <run> <unit> <sha>`; the reply is one line.
- `push approved for <unit> <sha7>, not seen yet`: `list_events` on the child (limit 5). Idle, with its last final message `[push-request]` for that sha: its answer poll died. If the unit holds the slot (or the queue is parallel), send it one message to read `<run>/pushes.log`; if it gave the slot up, send it one message to ask again. Otherwise nothing; it is syncing, validating or fixing, or waiting on the owner.
  For the integration unit, first check whether its push already landed: the child is at `[watching]` (`list_events`, limit 5), and with `<sha>` from its last `<unit> go` line in `pushes.log`, `git ls-remote origin refs/heads/integration/<slug>` gives a remote head that equals `<sha>` or has it as an ancestor (`git fetch origin integration/<slug>`, then `git merge-base --is-ancestor <sha> <remote head>`). Then run `run.py synced <run> <unit> <sha>`; the reply is one line. Otherwise follow the rest of this row. Its `go` holds every unit merge (`integration sync in flight`) until it lands, and in parallel mode no `STUCK … no-push` fires for it. With its session gone, or at `[blocked]`: `run.py redo <run> <unit> <sha> stuck`, `<sha>` from its last `<unit> go` line in `pushes.log`, which spends the `go`; tell the user in one line.
- `slot holder <unit> PR #<pr> behind base`: handle it as `BEHIND`, unless `list_events` on the child (limit 5) shows it already syncing.
- `<unit> can merge now its --after units merged: ask it to sync and push`: the unit lost the slot when it gained `--after`, and nothing else makes its child ask again. Send it one message: sync with `<base>` and ask to push. Skip it if `list_events` on the child (limit 5) shows it already syncing or asking.
- `slot free with a queue, next <unit> <sha>`: handle it as `NEXT`.
- `requests.log has lines no wait has read yet`: start a `wait`; it reports those you have not answered yet.
- `bad request line: …`: if a child wrote it, send that child one message with the exact request line format. Tell the user in one line otherwise. Once every listed line is handled, run `run.py clear-bad <run>`.
- `<unit> PR #<pr> targets <ref>, not <expected>: tell its child to retarget it` (integration mode): the PR is never reported ready on that base. Send the unit's child one message to run `gh pr edit <pr> -R <repo> --base <expected>`. Nothing else to do; the watcher reports it once it targets `<expected>`.
- `gate <unit> may open`: run `run.py open-ready <run>`.
- `final gate for <unit> may open: run open-ready` (integration mode): run `run.py open-ready <run>`.
- `every unit stopped: ask the owner what to do with <branch>` (integration mode): unless that item is already open (`run.py item list <run>`), file a `--run-wide` decision item: close the integration branch, or add units? Close: `run.py stop <run> integration every unit stopped` (the integration child's watch loop reads the stop line), close the final PR if one is open, and delete the branch (Finishing's command).

In integration mode, `run.py check <run>` can also print `NOT-READY <pr> head=<sha7> blocked: <reason>` or `FINAL-READY <pr> <sha>` (handle it as `FINAL-READY`). For `blocked: targets <ref>, not <expected>`, handle it as the `targets` line above; for any other reason there is nothing to do, since the watcher reports the PR again once the block clears.

| Event | Do |
|---|---|
| `REQUEST <unit> <sha> <branch>` or `PENDING <unit> <sha> <branch>` | "Answering a push request", below. Send the child no message. `PENDING` is a request still unanswered 15 minutes after its `REQUEST`: handle it exactly like `REQUEST`. |
| `NEXT <unit> <sha>` | The slot is free and this queued request is first. Answer it again (the child may have changed something): covered gets `go`, not covered gets `redo`. Do not tell the child to sync first; the `go` covers it. |
| `READY <unit> <pr> <sha>` or `REMIND <unit> <pr> <sha>` | Apply the merge bar (merge-bar.md) and merge. The child may be running; that does not matter. |
| `SYNCED <unit> <sha>` | The integration child pushed its `go` to the integration branch. `run.py synced <run> <unit> <sha>`. The reply is one line. |
| `FINAL-READY <unit> <pr> <sha>` | The final PR of an owner-merges run is ready. File it once as a decision item for the unit, with the PR link: the owner merges it. Close it (`run.py item done <run> <id>`) once the owner acknowledges it, and note `final PR #<pr> ready for you to merge` in `notes.md` for the tracker's `Elsewhere:` line; remove the note when it merges. Never merge it: the owner does, and the watcher's `MERGED` then leads to "After a merge" (merge-bar.md). |
| `open-ready` prints `<unit> final review` or `<unit> final no-review` | The final gate opened. Nothing to send; the integration child's poll reads it. |
| `MERGED <unit> <pr>` | If you already ran `run.py merged <run>` for that PR, ignore it. Otherwise someone else merged it: confirm with `gh pr view`, then "After a merge" (merge-bar.md). |
| `CLOSED <unit> <pr>` | `run.py closed <run> <unit> <pr>`, then file a decision item for the unit: is it dropped or redone? Its dependents stay gated meanwhile. A redone unit's new session gets its worktree recorded as the row on a card the user started says. |
| `BEHIND <unit> <pr> <sha>` | Send the child one message: sync with `<base>` and ask to push. For the integration unit: nothing; its watch loop syncs it. |
| `STUCK <unit> - syncing` | The integration child announced a conflicted base merge an hour ago and has not asked to push; every unit merge waits on it. `list_events` on the child (limit 5). Still resolving, reviewing or validating: nothing. At `[waiting]` or `[blocked]`, or its session gone or idle at anything else: `run.py redo <run> <unit> <sha> stuck`, `<sha>` from the `requests:` line `wait --full` printed (its last `<unit> syncing` line), which ends the hold; tell the user in one line. |
| `STUCK <unit> <pr> no-push` or `STUCK <unit> - no-push` | `list_events` on the child (limit 5). Idle at `[push-request] <sha>`, with the `pushes:` line `wait --full` printed being `<unit> go <sha>`, written after that request: its answer poll died. Do not yield; send it one message to read `<run>/pushes.log`. At `[pushing] <sha>`, or syncing, validating or pushing: nothing; it is acting on the `go`, and its push, its next request or a `STALLED` settles it. Only at `[waiting]` or `[blocked]`, or with its session gone or idle at anything else: `run.py yield <run> <unit> stuck`; a cause the owner must decide that is not an item yet: file a decision item for the unit. For the integration unit, the `yield` also spends its `go`, so unit merges stop waiting on it: its child checks that it is ahead of `origin/integration/<slug>` before it pushes and never force-pushes, so a late push of that `go` is rejected rather than landing under a unit merge. In parallel mode there is no slot and no such `STUCK`: see the `push approved for <unit>` line under "On every user message". |
| `STUCK <unit> <pr> <reasons>` (failing checks, unresolved threads, a conflict) | Serial mode: `run.py yield <run> <unit> stuck`. `list_events` on the child (limit 5); a cause the owner must decide that is not an item yet: file a decision item for the unit. Otherwise nothing; it asks again when it is ready. |
| `ORPHAN <unit> <pr>` | A PR opened on a done unit's branch after its last merge. File a decision item for the unit: what it changes (`gh pr view <pr> -R <repo>`), and merge or close it? Merge: the merge bar, with `run.py check <run> <unit>` for readiness, then `run.py merged <run> <unit> <pr>`. Close: `gh pr close <pr> -R <repo>`, then `run.py closed <run> <unit> <pr>`. In integration mode the final PR waits on the ORPHAN until `merged` or `closed` records it; run `run.py open-ready <run>` after either, since the final gate may be due. If the owner merges the final PR themself and was already told it is ready (`FINAL-READY`), tell them in one line not to merge it until the ORPHAN is settled, and say so in the ORPHAN item's body too. A done unit listed in `final PR #<pr> waits on <units>` is an ORPHAN not yet recorded; if `gh pr view <pr> -R <repo> --json state` shows it already merged or closed on GitHub, record that with `run.py merged <run>` or `run.py closed <run>`, since the watcher does not poll a reported ORPHAN again. |
| `STALLED <unit> <pr> head=<sha7><reasons>` | A unit held `answer sent:` (`status` lists its hold): `list_events` on the child (limit 5), then send it one message to apply the forwarded answer and ask to push again. Otherwise `list_events` on the child (limit 5). Legitimately waiting (on a decision, a review still running, CI queued): nothing. Otherwise tell the user what is stuck, in two lines. |
| `ERROR <message>` | Tell the user the line. `gh` failures: start the `wait` again. A run folder it cannot read: run `run.py status <run>` for the cause, and fix it or wait for the user before starting the `wait` again. |
| A one-line notice from the child of a unit the owner designs with it that a question in its own session blocks the merge | Note it under the unit's open questions in `notes.md`, marked `own session`. Not held: `run.py hold <run> <unit> own session: <topic>`. Held `answer sent:`: `run.py release <run> <unit>`, then `run.py hold <run> <unit> own session: <topic>`. Held for anything else: the note is enough, and the hold stays. Tell the user in one line where the question is; the tracker lists it under `Elsewhere:`. It is never an item. Its next push request settles it ("Answering a push request", step 5): it may not ask while the question is open. |
| Child message with an escalated review finding, a question or a command item, or a `[blocked]` message or note | File each item it carries (owner-queue.md: one `item add` per item, in order, with the child's recommendation and yours in its body), and reply as that section says. It blocks the merge when it is an escalated finding, when it says "blocks merge: yes", or when it is a question with no "blocks merge" marker. A `[blocked]` one blocks it only when it says "blocks merge: yes". A blocking one: file it `--blocks yes`, then `run.py hold <run> <unit> <short reason>`. If that refuses with `already held` and the hold's reason starts with `answer sent:`, run `run.py release <run> <unit>`, then the `hold` again, so `status` shows what it waits on; any other hold stays as it is. One that doesn't block ("blocks merge: no", or a `[blocked]` one with no marker): hold nothing; a `READY` that meets the merge bar is merged. A `[blocked]` one that doesn't block, while the unit holds the slot: `run.py yield <run> <unit> blocked`. |
| The user answers a question you relayed | Close the item as owner-queue.md says (`item done` with the owner's words, then the next item). Forward only on a `forward due <unit> <ids>` line, reading each answer from `<run>/items/<id>.answer.md`. An answer that approves work outside every unit becomes a card (the row on work outside every unit), whatever the unit's state; forward nothing to the child for it. Otherwise, if the unit's last PR has already merged, forward nothing: an answer that needs no work on that branch is only recorded, and one that needs work becomes a card (the row on work outside every unit). Otherwise send the child the rest in one message, quoting each answer's words with its `ref` (an escalated finding: the child records it with `--resolve`; it then asks to push again). Where the words leave how they apply to the code open, you may add your reading, labelled as yours and not the owner's; nothing else, reviews included. Then `run.py item forwarded <run> <unit>`, even when nothing was sent. If the unit is held, `run.py item list <run>` shows no open blocking item of it (current, queued or parked) and `notes.md` no `own session` question: `run.py release <run> <unit>`, then, if anything was sent, `run.py hold <run> <unit> answer sent: <topic>`. That hold ends at its next push request: part 8 has the child always ask again after a forwarded answer, with the same sha if nothing changed. Until then a `READY` on the old head can't merge. Add the decision to `notes.md` if later units need it. |
| A child message that says nothing waits on the answer | Apply what it asks (a `notes.md` entry, an `--after`) and send no reply. After an `--after`, run `run.py open-ready <run>`: the unit it now merges after may open past the WIP limit. |
| Any other child note (a child not detached yet, or one the app refused to detach) | Nothing. The reply stays one line, for a note from a child at `[designing]` too. |
| Work outside every unit turns up (in a note, message or PR) | Propose it as a card, once, as children.md ("A card for work outside every unit") says. It merges like any unit and gates nothing. |
| The app reports the user started a card from this run | `get_session` it. If the unit already has a worktree in `run.json`, run `run.py item list <run>` first. Then `run.py unit <run> <name> --branch <branch> --worktree <path>`; for a card for work outside every unit, which is not a unit yet, add `--title "<title>" --spec <path>`, as its `brief --card` had them. A new worktree drops the unit's open items from the old session: for each `dropped <id>` it prints, tell the owner in one line, with the item's summary from that `item list`, that it no longer applies. If the unit is held with a reason that starts with `answer sent:`, the new session never got that answer: `run.py release <run> <unit>`; if the answer still applies, send the new child one message quoting the owner's words from the unit's forwarded answers (`<run>/items/<id>.answer.md`), then `run.py hold <run> <unit> answer sent: <topic>`. Detach it (setup.md, step 6), then `run.py open-ready <run>`; fill in the table, and remove its card note from `notes.md`, if it has one. |
| The user adds a unit | This is the user's turn, so start it now. Run `run.py unit <run> <name> --prereq <units> --after <units> --title "<title>" --spec <spec path>` (only the options with something to give), then `run.py open-ready <run>`. If it will run beside an open unit, write its "Shared changes" first (setup.md, step 3). Start its session (children.md); its brief drops the gate (`--no-gate`) only if `open-ready` just opened it. If the user will design it with the child, follow "A unit the owner designs with the child" there. Record its branch and worktree, detach it (setup.md, step 6), and add it to the table in `notes.md`. In integration mode, if you already told the owner the final PR is ready (`FINAL-READY`), tell them in one line not to merge it until `<unit>` lands, and file that as a decision item for the integration unit, closed (`item done`) once the owner acknowledges it. Note `don't merge final PR #<pr> until <unit> lands` in `notes.md` for the tracker's `Elsewhere:` line; remove the note when `<unit>` lands. |
| The user adds a prerequisite to a unit | Not started yet (listed under `gated`): before `run.py unit <run> <unit> --prereq <units>`, tell the user in one line the wait it costs (until those units merge) and offer `--after` instead. When the conflict is merge order alone (the same docs or files, no code dependency), apply `--after` without asking. Already started: only `--after` applies; a `--prereq` does nothing once the gate is open. After any `--after`, run `run.py open-ready <run>`: the units it now merges after may open past the WIP limit. |
| The user changes the plan | WIP limit: `run.py set <run> wip <N\|none>`; lowering it never stops a unit already open. Queue mode: `run.py set <run> queue parallel` only when the owner asks; for each `queued <unit> <sha>` it prints, answer the request again ("Answering a push request": a fresh check, covered gets `go`). Cancel a unit: run `run.py status <run>` first. Listed under `gated`: `run.py stop <run> <unit> <reason>` alone. Listed under `open` (`<unit> PR #n` or `<unit> working`; it has started and never reads `gates.log` again): `run.py stop <run> <unit> <reason>`, then send its child one message that the unit is stopped, quoting the reason, and file a `--run-wide` decision item (`item add` refuses a stopped unit): close its open PR? Before either `stop`, run `run.py item list <run>` for the summaries; after it, tell the owner one line per `dropped <id>` it printed, with that item's summary, then run `run.py status <run>`. Update the table in `notes.md`. |

**Answering a push request** (`REQUEST` or `PENDING <unit> <sha> <branch>`, or `NEXT <unit> <sha>` with the unit's branch from `run.json` as `<branch>`). Work through these steps in order; the first `redo`, `go` or `queue` you run ends it:
1. The unit is done (you ran `run.py merged <run>` for its last PR; `run.py go <run>` refuses it too): `run.py redo <run> <unit> <sha> pr-merged`, then file a decision item for the unit: does the change become a follow-up (`list_events` on the child shows what it is)? The unit is stopped (`status` lists it `stopped`; `go` and `queue` refuse it): `run.py redo <run> <unit> <sha> unit-stopped`.
2. Read the unit's branch and worktree from `<run>/run.json` (under `units`). Either missing: `get_session` on the child and record them with `run.py unit <run> <unit> --branch <branch> --worktree <path>`, then detach the child (setup.md, step 6). Still no working directory: `run.py redo <run> <unit> <sha> no-worktree-path` and, unless that cause for the unit is already an open item (`run.py item list <run>`), file a decision item for the unit.
3. The check: the `verdict` line `wait --full` printed, when it is a JSON verdict for `<sha>` (SKILL.md, the verdict rule), is the check JSON. Otherwise (`unavailable`, another sha, or a request found through `status`), invoke `branch-review:check --repo <worktree> --commit <sha>`. The check errors (exit 1): `run.py redo <run> <unit> <sha> check-error` and, unless that cause for the unit is already an open item (`run.py item list <run>`), file a decision item for the unit, quoting its stderr line.
4. The check JSON's `branch` differs from the request's branch or from the unit's branch in `run.json`: `run.py redo <run> <unit> <sha> wrong-branch`. For the integration unit, also `git -C <worktree> fetch origin <integration branch>`; if `git -C <worktree> merge-base --is-ancestor origin/<integration branch> <sha>` fails, a unit merged after its merge: `run.py redo <run> <unit> <sha> behind-integration`.
5. The unit is held (`status` lists `hold <unit>: <reason>`), whatever the reason: strike the questions marked `own session` from the unit's open questions in `notes.md`, since the child may not ask while one is open. None left open, and `run.py item list <run>` shows no open blocking item of the unit (current, queued, parked, or answered and not forwarded): `run.py release <run> <unit>`, then go on to step 6. Otherwise: `run.py redo <run> <unit> <sha> held`.
6. Covered: `run.py go <run> <unit> <sha>`. If it refuses with `unit '<unit>' is held:`, handle it as step 5. If it refuses because another unit holds the slot or is first in the queue, or (serial mode) because the unit `merges after` a unit not yet merged: `run.py queue <run> <unit> <sha>`. For `merges after`, `queue` works for the slot holder too: it gives up the slot and is queued.
7. Not covered: `run.py redo <run> <unit> <sha> '<reasons>'`, `<reasons>` the JSON's `reasons` joined by `, ` (no `not covered: ` prefix).

Once a `no-worktree-path` or `check-error` is sorted out, close its item and send the child one message to ask again.

**Messages** go to a child only for what no file carries: an owner answer, a `BEHIND` sync, a merged part k of N, a dead poll, a request format fix, a merge bar the check failed, a stopped unit that had started, a PR to retarget. Never send one alongside a `go`, `redo` or `open`, or a `stop` to a unit still gated: the child's poll reads the file within a minute. A started unit's `stop` is the one exception, since nothing polls `gates.log` for it any more. Never mention reviews; `redo` reasons say when one is needed. A gated child gets a message only if it is still `[gated]` 5 minutes or more after its gate opened: its gate loop died, so tell it its gate is open.

## Red flags

| Thought | Reality |
|---|---|
| "I'll wait for the child's note" | Detached children send none, and notes can be held for hours. Act on the watcher's lines, child messages and `run.py status`. |
| "`STUCK … no-push`: yield, then tell the child to read `pushes.log`" | A dead poll is the likely cause. After a yield, that old `go` would push without the slot. Message only, no yield. |
| "`STUCK … no-push` and the child is syncing; yield" | It is acting on the `go`. Yield only when it is at `[waiting]` or `[blocked]`, or gone. |
| "8.6 conflicts with 8.7, add a prereq" | `--after` if it's only merge order. A prerequisite keeps the unit gated until the other merges. |
| "The child says nothing waits on me; I'll confirm" | No reply. Apply what it asks and spend no send. |
| "The child gave a status update; I'll summarize it for the user" | One line at most, nothing about progress. |
