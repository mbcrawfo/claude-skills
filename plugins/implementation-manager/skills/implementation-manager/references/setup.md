# Setup (first turn)

Only in the first turn of a run. A turn after a compaction never runs Setup again.

1. **The work breakdown.** Use this conversation's plan if it has one; otherwise read the spec, plan or epic named in the arguments. List the units: name (short, letters, digits, `-` and `_`, e.g. `5-3`), title, spec path, prerequisites, merge-order units, and a `branch_name` you choose. A prerequisite (`--prereq`) is code the unit builds on: its gate waits for it. A merge-order unit (`--after`) is an order that only matters at merge, such as changes to the same docs or files: the unit starts at once and merges after it. Take order and dependencies from the docs; units the docs allow side by side run in parallel. If this session has its own open PR the units need (e.g. the specs), it is a unit named `specs` with no child, and every unit depends on it.
2. **Repository facts and review tools:** `owner/repo`, base branch, and merge method (the repository's instructions; otherwise `gh repo view --json mergeCommitAllowed,squashMergeAllowed,rebaseMergeAllowed`, and if more than one is allowed and nothing says which, ask). Confirm `branch-review:check` and `branch-review:review` are among your available skills. If either is missing, stop and tell the user to install branch-review (`/plugin install branch-review@mbcrawfo-skills`). Load `branch-review:check` once, now: its command shows the full path of its `rs` script and its `CLAUDE_PLUGIN_DATA` folder with the placeholders filled in. Note both for step 3. Also note the repository facts every child needs: its formatter, its validation commands, and its PR rules.
3. **The run folder:** `<run>` is the path SKILL.md's "The run script and the run folder" gives, written out in full; if it does not start with `/`, stop as that section says. First run the prune command exactly as SKILL.md writes it, `run.py prune <run> --days` with the retention option in single quotes: it removes this repo's runs untouched for the retention period, never `<run>`, and prints one JSON object. Print each path in `removed`. If it exits 1 after its JSON, print each entry in `errors`; if it exits non-zero with no JSON, print its stderr line. Either way go on, since a failed prune does not affect this run. Then run `run.py init <run>` with `--repo`, `--base` and `--method` from step 2 and `--wip N` if the owner gave a WIP limit. Then `run.py check-cmd <run> --rs <the rs path> --state-dir <the CLAUDE_PLUGIN_DATA folder>`, both from step 2, and `run.py set <run> manager <your id>`, your id from `get_session` with `"self"`. Write `<run>/facts.md` with the repository facts from step 2; every child's brief includes it. Then `run.py unit <run> <name> --prereq <units> --title "<title>" --spec <spec path>` for each unit in table order, leaving out an option with nothing to give (`run.py unit <run> specs --specs` first if there is a `specs` unit). Once every unit exists, add the merge-order units in a second pass, `run.py unit <run> <name> --after <units>`: `unit` refuses an `--after` that names a unit not added yet. Write `<run>/notes.md` with the units table: name, title, spec, prerequisites, merge-order units, session, branch, PRs; and an empty `## Decisions` section (SKILL.md, "Decisions"). Put the app's shared notes folder (where children write `<unit>-notes.md`) at its top once you know it: look among your own additional working directories, or in a child's first prompt after step 5.
   **Shared changes.** Before two gates open whose units the docs allow side by side, and before a unit added mid-run starts beside an open one, read both specs and add a "Shared changes" section to `notes.md`: the files or modules both will change, which unit owns each change, and its agreed shape where the specs say it. Part 6 of each sibling's prompt points at it.
4. **Go or ask.** If the breakdown and dependencies are stated in the docs or were agreed in this conversation, continue. If you inferred any dependency, or anything in steps 1–2 is ambiguous, show the units table and ask; start everything on the user's answer.
5. **Start every child now** (see children.md). Every child's prompt carries its gate. If any start comes back as a card instead, say so and note it in `notes.md`; the tracker lists it under `Elsewhere:` until the app reports it started.
6. **Record, detach and watch.** `get_session` on each child for its actual branch (the app adds a prefix and suffix) and working directory, and run `run.py unit <run> <name> --branch <branch> --worktree <path>`; if either is not set yet, do it next turn. Once a child is recorded, detach it: `mcp__ccd_session_mgmt__detach_session` with its session id (load it with ToolSearch if it is deferred). The app then stops telling you when its turns end; `get_session`, `list_events`, messages by id and `archive_session` still work, and its id stays in `notes.md`. If the app refuses or lacks the tool, carry on: its notes are harmless, since the "Any other child note" row (events.md) ignores them. For `specs`, record this session's own branch and working directory. Then start one `run.py wait <run> --full` with `run_in_background`.
7. Run `run.py open-ready <run>` and reply with the tracker.

### Integration-branch mode

Only when the owner asks for it. The units merge into `integration/<slug>` instead of `<base>`, and one final PR from it lands the whole run in `<base>`. `<base>` stays the base of the final PR; wherever these instructions have a unit, a card, the `specs` unit or a message to a unit's child use `<base>` for the units' work, use `integration/<slug>` instead. Choose `<slug>` (the slug of the work that names the run folder in step 3) in step 2, before the checks below. These steps add to the ones above:

- **Choices,** before step 3. Unless the owner said, ask in the reply text who merges the final PR (`manager` once it meets the merge bar, or `owner`) and whether to run a whole-feature review before it. Never assume either; setup waits for the answer.
- **Merge method,** in step 2. Choose `merge` or `squash`, never `rebase`: the final PR carries the integration child's base-merge commits, which a rebase merge flattens or refuses, and `init` refuses `--method rebase` with `--integration`. If the repository allows only rebase merges, tell the owner and stop.
- **Default branch,** in step 2. `<base>` must be the repository's default branch (`gh repo view <repo> --json defaultBranchRef --jq .defaultBranchRef.name`): `sync_with_base_branch` merges only that branch into the integration branch. If it is not, tell the owner and stop.
- **CI check,** in step 2. Read the `pull_request` triggers of the repository's workflows (`.github/workflows/`). If their branch filters exclude `integration/<slug>`, tell the owner and stop: unit PRs would never get checks, so they would never be ready.
- **Skills,** in step 2. Also confirm `branch-review:record` is among your available skills, next to `check` and `review`; if it is missing, stop and tell the user to update branch-review to 0.10.0 or later.
- **Create the branch,** in step 3, before `init` and before starting any session. You create it; the integration child does not. `gh api repos/<repo>/git/refs -f ref=refs/heads/integration/<slug> -f sha=<base head>`, `<base head>` from `git ls-remote origin refs/heads/<base>`. Then `git fetch origin integration/<slug>:integration/<slug>`, so a local branch exists for `source_branch`.
- **Planning commits as the branch's start,** when the owner asks for them instead of a `specs` PR. Commit the spec or plan on this session's branch, on top of `<base head>`, and validate as the repository requires. With feature review `no`, also run `/branch-review:review --base origin/<base>` on it to convergence: nothing else will review it. Then create the branch by pushing that commit, instead of the `gh api` call: `git push origin <the commit>:refs/heads/integration/<slug>` (GitHub cannot create a ref at a commit it does not have yet), then the `git fetch` above. There is no `specs` unit. Record in `notes.md` which commits these are and what reviews them (that review, or the whole-feature review).
- **Init,** in step 3. `run.py init <run>` with `--repo`, `--base` and `--method` from step 2 plus `--integration integration/<slug> --final-merge <manager|owner> --feature-review <yes|no>`. Then, after `run.py unit <run> specs --specs` if there is one and before the other units, `run.py unit <run> integration --integration --title "integration" --spec <the spec, plan or epic the run implements>`. Add the integration child to the units table in `notes.md`.
- **Planning PR,** in step 3. If the `specs` PR is open against `<base>`, retarget it: `gh pr edit <pr> -R <repo> --base integration/<slug>`. Its review uses `--base origin/integration/<slug>` from then on. A `specs` PR opened later targets `integration/<slug>`.
- **Start,** in step 5. Start the integration child first (children.md), then every unit child, all with `source_branch: integration/<slug>` beside the other `start_session` arguments.
- **Record,** in step 6. For the integration unit, record only `--worktree`: `--integration` set its branch, and `unit` refuses any other. Do the same wherever these instructions record a unit's branch and worktree.

## Red flags

| Thought | Reality |
|---|---|
| "Detaching hides the children; I'll keep them nested" | Their notes cost a turn each and carry nothing you act on. Detach each one once it is recorded. |
