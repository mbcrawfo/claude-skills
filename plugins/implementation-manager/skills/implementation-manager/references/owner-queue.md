# The owner queue

Everything that waits on the owner is an item in `run.py item`, never straight in the reply text. The owner sees one item at a time, and a unit's items together.
- **Filing.** Write the body to a file outside the repository (this session's scratchpad if it has one, otherwise `<run>/`): the question, or the command to run and why; a finding's `fix_options` quoted word for word; the child's recommendation and yours. Then `run.py item add <run> <unit> --ref Q<n> --kind <kind> --blocks <yes|no> [--depends Q<m> ...] --summary "<one line>" --body-file <file>`. A "decision item" is one of yours, `--kind decision --blocks no` with no `--ref`, its body what the owner must decide and your recommendation; `--run-wide` in place of the unit when it belongs to none.
- **Splitting.** A child message with several items becomes one `item add` per item, in order. Read `ref`, kind, `blocks merge` and `depends on` from each item's header line; an escalated finding is `--blocks yes`. An item with no header gets no `--ref` and no `--depends`, takes its kind from its text, and blocks unless it says "blocks merge: no". A ref refused as already used: the same item sent again files nothing; a different one is filed with no `--ref`. A `--depends` refused (the ref is not in the unit's current session generation): file the item without `--depends`; when parking, add it with `--with` if it plainly builds on a parked item.
- **Showing.** `item add` printed `current …`: run `run.py item current <run>` and show it in full, then one line, `<N> more waiting: <unit> ×<n>, …` (from `status`'s `- items:` line), with the parked count if any. It printed `queued …`: the reply about it is one line, `queued for <unit>, <N> waiting`. `parked <id> with <parent>`: one line saying so.
- **Answers.** An owner reply that answers the current item: write the owner's words to a file outside the repository, `run.py item done <run> <id> --answer-file <file>`, then show the next item as above. A reply that asks back keeps the item current: answer it first. A command item is done when the owner says it ran; pasted output goes in the answer file. The owner may answer a queued item by name; `item done` takes it. A decision item: `run.py item done <run> <id>` first, then do what the owner chose, as its row says. The order matters when the choice stops the item's own unit: `stop` drops the unit's open items, so a decision still open would be dropped rather than closed, and it is not one of the `dropped` lines to report. One for something the owner does outside the conversation (merge the final PR, or hold off merging it) is done once the owner acknowledges it, with any reply about it that is not a question back.
- **Parking.** "Park this" and the like: `run.py item park <run> <id> <note>`; add `--with <ids>` for unmarked items that plainly build on it, and say so in one line. "Keep it": `run.py item unpark <run> <id> --queue`. "Back to <id>": `run.py item unpark <run> <id>`, then show it. The child is not told, and a hold stays as it is.
- **Forwarding.** Never forward before a `forward due <unit> <ids>` line (from `item done`, `item park` or `status`). On each one, first the exceptions: an answer that approves work outside every unit becomes a card, whatever the unit's state; and if the unit's last PR has already merged, nothing is sent: an answer that needs no work on that branch is only recorded, and one that needs work becomes a card (the row on work outside every unit). Otherwise send the unit's child one message quoting each answer from `<run>/items/<id>.answer.md` with its `ref` (its summary when it has none). Then run `run.py item forwarded <run> <unit>`, even when nothing was sent, then the hold steps of the "The user answers a question you relayed" row (events.md).
- **Stale items.** After a merge, drop the unit's items that no longer matter (`run.py item drop <run> <id> <reason>`) and say so in one line each. `stop` and a new worktree (`unit --worktree`) drop items themselves: run `run.py item list <run>` before them, then say one line per `dropped <id>` they print, with that item's summary. After any of these, run `run.py status <run>` for the new current item and any `forward due`.
- **Older runs.** A run begun before 0.8.0 kept open questions in `notes.md`. When `notes.md` lists a unit's open questions not marked `own session` that have no item, file each one with `item add` (no `--ref`; kind and blocks from its text, and a question with no marker blocks), then strike it from `notes.md`. If `item add` refuses it (a stopped unit), strike it all the same, marked `not filed: <the refusal>`, and tell the owner in one line; never retry it.
- **AFK return.** On any owner message that does not answer or discuss the current item ("back", "what's next", an unrelated instruction), handle it, then end the reply with the current item in full and the count. "What's waiting?": `run.py item list <run>`, one line per item.

**Questions to the owner** are items (this file). Never use the pop-up question tool: while it waits, no event is handled. The answer arrives as a normal user message.

## Red flags

| Thought | Reality |
|---|---|
| "I'll ask the owner with the question tool" | It blocks every event behind it. File an item; the answer comes as a normal message. |
| "Three new questions came in; I'll show them all" | One current item. The rest are queued; say how many. |
| "I'll forward this answer now" | Only on `forward due`: one message per unit. |
| "The owner is back; I'll summarize the queue" | Show the current item in full, with the count. |
