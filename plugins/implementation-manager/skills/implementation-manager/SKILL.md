# Implementation Manager

<!-- Editing note: never write a dollar sign followed by a digit in this file. Claude Code replaces it with a skill argument when the skill loads. -->

This session takes planned work from spec to merged code. It starts one child session per unit of work (a phase or sub-phase), clears each child's pushes against branch-review's state, merges each child's pull request when it is ready, and releases the units that depend on it. It writes no product code. Its own planning PR, if one is open, is the one PR it works on itself: it keeps Auto-fix on for it, fixes every finding (thread or review body), reviews it with `/branch-review:review` and gates each push with `branch-review:check`, like a child's. The user is needed only for questions and problems.

**Invoking this skill authorizes** starting the child sessions and merging the run's PRs (the children's, cards the user starts from this run, and this session's own planning PR) once they meet the merge bar. It authorizes nothing else. When the owner asks for integration-branch mode, that request also authorizes creating the integration branch and deleting it once the final PR merges.

Arguments: `$ARGUMENTS`

## Four constraints that shape everything

1. **Sessions can only be started on the user's own turn.** `start_session` with `"user_asked"` is refused on a turn started by a background task, a child's note or another session's message; it degrades to a card the user must click. So **start every child in the first turn**, and hold each one back with a *gate* (a file the child polls), not by starting it later.
2. **Messages are a scarce budget.** The app stops delivering a session's messages after 10 sends without the user typing in it. Coordinate through files in the run folder (gates, push requests and answers), never through status messages.
3. **Nothing notifies you of a push request, a ready PR or a merge** except the run watcher: `python3 ${CLAUDE_SKILL_DIR}/../../scripts/run.py wait <run>` with `run_in_background`. It prints one event line and exits. Handle the event, then start it again before ending the turn. With open units and no `wait` running, the run is deaf.
4. **Child notes carry nothing you need.** The app sends you a note each time a child's turn ends, and a child ends a turn at every subagent dispatch, so they run to dozens per child. It may also hold them for hours and deliver only the latest. Nothing waits on a note: children write push requests to `<run>/requests.log`, send questions and `[blocked]` as messages, and you act on the watcher's lines, those messages and `run.py status`. So you detach each child once it is recorded (Setup, step 6), which stops its notes.

## The run script

`run.py <command> <args>` below is short for `python3 ${CLAUDE_SKILL_DIR}/../../scripts/run.py <command> <run> <args>`: the absolute run folder always comes right after the command. Write it out in full each time; shell variables do not survive between Bash calls. Only the script writes `run.json`, `gates.log` and `pushes.log`; never write them yourself. A refused command exits 1 with one line on stderr and changes nothing.

| Command | Does |
|---|---|
| `init --repo <owner/repo> --base <base> --method <merge\|squash\|rebase> [--wip N]` | Creates the run folder. The queue is `serial` (one PR in flight) unless the owner asks for `--queue parallel`. |
| `unit <name> [--prereq U ...] [--after U ... \| --after none] [--title T] [--branch B] [--worktree P] [--specs]` | Adds a unit (letters, digits, `-` and `_`), or updates the fields given. `--after` units must merge first, but don't gate the start; a stopped one counts as merged, and `--after none` clears the list. A unit can't both need and merge after the same unit, and cycles are refused. Each `--after` unit must already exist. Giving the slot holder an `--after` unit not yet merged frees the slot. `--title` is shown beside the name in `status`. |
| `set wip <N\|none>`, `set queue <serial\|parallel>` | The owner's changes mid-run. In parallel mode it prints `queued <unit> <sha>` for each request still queued. |
| `open-ready` | Opens every gate that may open now (prerequisites merged, within the WIP limit) and prints their names. A unit that an open unit merges after, and every unit that one needs or merges after in turn (none through a stopped unit), may open past the WIP limit, in the same call. |
| `open <unit>`, `stop <unit> <reason>` | Opens one gate; stops a unit for good (it never opens, gets `go` or queues again, and gives up the slot). |
| `go <unit> <sha>` | Allows the push. It refuses a held unit. In serial mode it also gives the unit the slot, and refuses while another unit holds it or is first in the queue, or while the unit merges after a unit not yet merged. |
| `queue <unit> <sha>` | Holds a covered request until the slot frees; the watcher then reports `NEXT`. A queued unit whose `--after` units haven't merged is skipped at the head, so the next one is served. It refuses a held unit. The slot holder can be queued only when it merges after a unit not yet merged; it gives up the slot. |
| `redo <unit> <sha> <reasons>` | Refuses the push with one line of reasons. A slot holder gives up the slot; an earlier `go` not yet pushed is spent. |
| `hold <unit> <reason>` | Holds the unit's merge until `release`, `merged`, `closed` or `stop`: no READY or REMIND, no STALLED unless the reason starts with `answer sent:`, and `go` and `queue` refuse it. It frees the slot if the unit holds it, drops its queue entry, and answers each waiting request (unanswered or queued) `redo <sha> held`. A done unit can't be held. |
| `release <unit>` | Lifts the hold and restarts the stall clock; a PR reported `READY` before the hold is reported again. |
| `yield <unit> <reason>` | The slot holder gives up the slot. Its PR stays open; it returns to the front of the queue when it asks again. A `go` it has not pushed stays outstanding: its old head is not reported ready. The integration unit's `go` stops holding unit merges, though (see the `STUCK … no-push` row). |
| `merged <unit> <pr> [--more]`, `closed <unit> <pr>` | Records a merge (`--more`: a part k of N with k < N) or a close, and frees the slot. |
| `status` | The tracker and every line under "needs the manager". |
| `clear-bad` | Forgets the bad request lines `status` lists, once you have handled them. |
| `check <unit>` | One readiness check of the unit's PR now: `READY <pr> <sha>`, `NOT-READY …`, `MERGED <pr>`, `CLOSED <pr>` or `ERROR …`. |
| `wait [--stall-hours N]` | Blocks until one event, prints it, exits 0. Always with `run_in_background`. |

Integration-branch mode only (see "Integration-branch mode" under Setup):

| Command | Does |
|---|---|
| `init … --integration integration/<slug> --final-merge <manager\|owner> --feature-review <yes\|no>` | Turns the mode on. All three options or none; there is no default for either choice. Refused with `--method rebase`. |
| `unit <name> --integration` | Makes the unit the run's one integration unit. Its branch is the integration branch and may be nothing else; it has no `--prereq` or `--after`, and no unit may name it in either. `open-ready` opens its gate at once, outside the WIP limit. |
| `set final-merge <manager\|owner>`, `set feature-review <yes\|no>` | The owner's changes to the two choices. Refused once the final gate has opened. |
| `synced <unit> <sha>` | The integration unit pushed its `go` straight to the integration branch: clears the `go` and frees the slot if it holds it. A unit PR reported `READY` while the sync was in flight is reported `READY` again. Refuses another unit, or a sha that is not its outstanding `go`. |
| (request line) `<unit> syncing <sha> <branch>` | Written by the integration child, not you, when its base merge conflicts. It holds unit merges (`integration sync in flight`, also for a line no `wait` has read yet) until its next push request, a `redo`, `stop`, `merged` or `closed`. `wait` reports `STUCK <unit> - syncing` once if no push request follows within an hour. From any other unit it is a bad line. |
| `open-ready` | Also prints `<unit> final review` or `<unit> final no-review` (and logs it to `gates.log`), once, when every other unit is done or stopped and at least one is done. |
| `check <unit>` | Also prints `NOT-READY <pr> head=<sha7> blocked: <reason>` while an integration block applies or the PR targets the wrong base (`targets <ref>, not <expected>`), and `FINAL-READY <pr> <sha>` for the final PR of an owner-merges run. |

## Setup (first turn)

1. **The work breakdown.** Use this conversation's plan if it has one; otherwise read the spec, plan or epic named in the arguments. List the units: name (short, letters, digits, `-` and `_`, e.g. `5-3`), title, spec path, prerequisites, merge-order units, and a `branch_name` you choose. A prerequisite (`--prereq`) is code the unit builds on: its gate waits for it. A merge-order unit (`--after`) is an order that only matters at merge, such as changes to the same docs or files: the unit starts at once and merges after it. Take order and dependencies from the docs; units the docs allow side by side run in parallel. If this session has its own open PR the units need (e.g. the specs), it is a unit named `specs` with no child, and every unit depends on it.
2. **Repository facts and review tools:** `owner/repo`, base branch, and merge method (the repository's instructions; otherwise `gh repo view --json mergeCommitAllowed,squashMergeAllowed,rebaseMergeAllowed`, and if more than one is allowed and nothing says which, ask). Confirm `branch-review:check` and `branch-review:review` are among your available skills. If either is missing, stop and tell the user to install branch-review (`/plugin install branch-review@mbcrawfo-skills`).
3. **The run folder:** `<run>` is `${CLAUDE_PLUGIN_DATA}/<owner>-<repo>/<slug>`, `<slug>` a slug of the work (e.g. `query-gen-phase-5`). It is an absolute path; write it out in full wherever `<run>` appears. If that path does not start with `/`, the plugin's data folder is unknown: stop and tell the user, and never pick a folder of your own. Run `run.py init` with the facts from step 2 and `--wip N` if the owner gave a WIP limit. Then `run.py unit <name> --prereq <units> --title "<title>"` for each unit in table order, leaving out an option with nothing to give (`run.py unit specs --specs` first if there is a `specs` unit). Once every unit exists, add the merge-order units in a second pass, `run.py unit <name> --after <units>`: `unit` refuses an `--after` that names a unit not added yet. Write `<run>/notes.md` with the units table: name, title, spec, prerequisites, merge-order units, session, branch, PRs. Put the app's shared notes folder (where children write `<unit>-notes.md`) at its top once you know it: look among your own additional working directories, or in a child's first prompt after step 5.
   **Shared changes.** Before two gates open whose units the docs allow side by side, and before a unit added mid-run starts beside an open one, read both specs and add a "Shared changes" section to `notes.md`: the files or modules both will change, which unit owns each change, and its agreed shape where the specs say it. Part 6 of each sibling's prompt points at it.
4. **Go or ask.** If the breakdown and dependencies are stated in the docs or were agreed in this conversation, continue. If you inferred any dependency, or anything in steps 1–2 is ambiguous, show the units table and ask; start everything on the user's answer.
5. **Start every child now** (see "Starting children"). Every child's prompt carries its gate. If any start comes back as a card instead, say so and list it under "Waiting on you" in the tracker.
6. **Record, detach and watch.** `get_session` on each child for its actual branch (the app adds a prefix and suffix) and working directory, and run `run.py unit <name> --branch <branch> --worktree <path>`; if either is not set yet, do it next turn. Once a child is recorded, detach it: `mcp__ccd_session_mgmt__detach_session` with its session id (load it with ToolSearch if it is deferred). The app then stops telling you when its turns end; `get_session`, `list_events`, messages by id and `archive_session` still work, and its id stays in `notes.md`. If the app refuses or lacks the tool, carry on: its notes are harmless, since "Any other child note" ignores them. For `specs`, record this session's own branch and working directory. Then start one `run.py wait` with `run_in_background`.
7. Run `run.py open-ready` and reply with the tracker.

### Integration-branch mode

Only when the owner asks for it. The units merge into `integration/<slug>` instead of `<base>`, and one final PR from it lands the whole run in `<base>`. `<base>` stays the base of the final PR; wherever this skill has a unit, a card, the `specs` unit or a message to a unit's child use `<base>` for the units' work, use `integration/<slug>` instead. Choose `<slug>` (the slug of the work that names the run folder in step 3) in step 2, before the checks below. These steps add to the ones above:

- **Choices,** before step 3. Unless the owner said, ask in the reply text who merges the final PR (`manager` once it meets the merge bar, or `owner`) and whether to run a whole-feature review before it. Never assume either; setup waits for the answer.
- **Merge method,** in step 2. Choose `merge` or `squash`, never `rebase`: the final PR carries the integration child's base-merge commits, which a rebase merge flattens or refuses, and `init` refuses `--method rebase` with `--integration`. If the repository allows only rebase merges, tell the owner and stop.
- **Default branch,** in step 2. `<base>` must be the repository's default branch (`gh repo view <repo> --json defaultBranchRef --jq .defaultBranchRef.name`): `sync_with_base_branch` merges only that branch into the integration branch. If it is not, tell the owner and stop.
- **CI check,** in step 2. Read the `pull_request` triggers of the repository's workflows (`.github/workflows/`). If their branch filters exclude `integration/<slug>`, tell the owner and stop: unit PRs would never get checks, so they would never be ready.
- **Skills,** in step 2. Also confirm `branch-review:record` is among your available skills, next to `check` and `review`; if it is missing, stop and tell the user to update branch-review to 0.10.0 or later.
- **Create the branch,** in step 3, before `init` and before starting any session. You create it; the integration child does not. `gh api repos/<repo>/git/refs -f ref=refs/heads/integration/<slug> -f sha=<base head>`, `<base head>` from `git ls-remote origin refs/heads/<base>`. Then `git fetch origin integration/<slug>:integration/<slug>`, so a local branch exists for `source_branch`.
- **Planning commits as the branch's start,** when the owner asks for them instead of a `specs` PR. Commit the spec or plan on this session's branch, on top of `<base head>`, and validate as the repository requires. With feature review `no`, also run `/branch-review:review --base origin/<base>` on it to convergence: nothing else will review it. Then create the branch by pushing that commit, instead of the `gh api` call: `git push origin <the commit>:refs/heads/integration/<slug>` (GitHub cannot create a ref at a commit it does not have yet), then the `git fetch` above. There is no `specs` unit. Record in `notes.md` which commits these are and what reviews them (that review, or the whole-feature review).
- **Init,** in step 3. `run.py init` with the facts from step 2 plus `--integration integration/<slug> --final-merge <manager|owner> --feature-review <yes|no>`. Then, after `run.py unit specs --specs` if there is one and before the other units, `run.py unit integration --integration --title "integration"`. Add the integration child to the units table in `notes.md`.
- **Planning PR,** in step 3. If the `specs` PR is open against `<base>`, retarget it: `gh pr edit <pr> -R <repo> --base integration/<slug>`. Its review uses `--base origin/integration/<slug>` from then on. A `specs` PR opened later targets `integration/<slug>`.
- **Start,** in step 5. Start the integration child first ("The integration child"), then every unit child, all with `source_branch: integration/<slug>` beside the other `start_session` arguments.
- **Record,** in step 6. For the integration unit, record only `--worktree`: `--integration` set its branch, and `unit` refuses any other. Do the same wherever this skill records a unit's branch and worktree.

9. Status token. Every turn's final message begins with one of `[gated]`, `[designing]` (a unit the owner designs with you, while designing), `[building]`, `[reviewing]` (running `/branch-review:review`), `[fixing]`, `[push-request] <sha>` (asking to push that full sha), `[pushing] <sha>` (acting on a `go`: syncing, validating, pushing), `[waiting]` (on a decision or the manager), `[blocked]`, or `[review]` (PR open and nothing left for you to do unless review or CI reports something). If the unit holds the slot (or the queue is parallel), send it one message to read `<run>/pushes.log`; if it gave the slot up, send it one message to ask again. Otherwise nothing; it is syncing, validating or fixing, or waiting on the owner.
  For the integration unit, first check whether its push already landed: the child is at `[watching]` (`list_events`, limit 5), and with `<sha>` from its last `<unit> go` line in `pushes.log`, `git ls-remote origin refs/heads/integration/<slug>` gives a remote head that equals `<sha>` or has it as an ancestor (`git fetch origin integration/<slug>`, then `git merge-base --is-ancestor <sha> <remote head>`). - `slot free with a queue, next <unit> <sha>`: handle it as `NEXT`.
- `requests.log has lines no wait has read yet`: start a `wait`; it reports those you have not answered yet.
- `bad request line: …`: if a child wrote it, send that child one message with the exact request line format. Tell the user in one line otherwise. Once every listed line is handled, run `run.py clear-bad`.

- `gate <unit> may open`: run `run.py open-ready`.
- `final gate for <unit> may open: run open-ready` (integration mode): run `run.py open-ready`.
- `every unit stopped: ask the owner what to do with <branch>` (integration mode): ask the owner, in the reply text and under "Waiting on you", whether to close the integration branch or add units. | The user adds a unit | This is the user's turn, so start it now. Run `run.py unit <name> --prereq <units> --after <units> --title "<title>"` (only the options with something to give), then `run.py open-ready`. If it will run beside an open unit, write its "Shared changes" first (Setup, step 3). Start its session ("Starting children"); its prompt drops the gate part only if `open-ready` just opened it. If the user will design it with the child, follow "A unit the owner designs with the child". Record its branch and worktree, detach it (Setup, step 6), and add it to the table in `notes.md`. In integration mode, if you already told the owner the final PR is ready (`FINAL-READY`), tell them in one line not to merge it until `<unit>` lands, and list that under "Waiting on you". |
| The user adds a prerequisite to a unit | Not started yet (listed under `gated`): before `run.py unit <unit> --prereq <units>`, tell the user in one line the wait it costs (until those units merge) and offer `--after` instead. When the conflict is merge order alone (the same docs or files, no code dependency), apply `--after` without asking. Already started: only `--after` applies; a `--prereq` does nothing once the gate is open. After any `--after`, run `run.py open-ready`: the units it now merges after may open past the WIP limit. |
| The user changes the plan | WIP limit: `run.py set wip <N\|none>`; lowering it never stops a unit already open. Queue mode: `run.py set queue parallel` only when the owner asks; for each `queued <unit> <sha>` it prints, answer the request again ("Answering a push request": a fresh check, covered gets `go`). Cancel a unit: run `run.py status` first. Listed under `gated`: `run.py stop <unit> <reason>` alone. Listed under `open` (`<unit> PR #n` or `<unit> working`; it has started and never reads `gates.log` again): `run.py stop <unit> <reason>`, then send its child one message that the unit is stopped, quoting the reason, and ask the owner whether to close its open PR. Update the table in `notes.md`. |

**Answering a push request** (`REQUEST` or `PENDING <unit> <sha> <branch>`, or `NEXT <unit> <sha>` with the unit's branch from `run.json` as `<branch>`). Work through these steps in order; the first `redo`, `go` or `queue` you run ends it:
1. The unit is done (you ran `run.py merged` for its last PR; `run.py go` refuses it too): `run.py redo <unit> <sha> pr-merged`, then ask the owner whether the change becomes a follow-up (`list_events` on the child shows what it is). The unit is stopped (`status` lists it `stopped`; `go` and `queue` refuse it): `run.py redo <unit> <sha> unit-stopped`.
2. Read the unit's branch and worktree from `<run>/run.json` (under `units`). Either missing: `get_session` on the child and record them with `run.py unit <unit> --branch <branch> --worktree <path>`, then detach the child (Setup, step 6). Still no working directory: `run.py redo <unit> <sha> no-worktree-path` and tell the user in one line.
3. Invoke `branch-review:check --repo <worktree> --commit <sha>`. It errors (exit 1): `run.py redo <unit> <sha> check-error` and tell the user its stderr line.
4. The check JSON's `branch` differs from the request's branch or from the unit's branch in `run.json`: `run.py redo <unit> <sha> wrong-branch`. For the integration unit, also `git -C <worktree> fetch origin <integration branch>`; if `git -C <worktree> merge-base --is-ancestor origin/<integration branch> <sha>` fails, a unit merged after its merge: `run.py redo <unit> <sha> behind-integration`.
5. The unit is held (`status` lists `hold <unit>: <reason>`), whatever the reason: strike the questions marked `own session` from the unit's open questions in `notes.md`, since the child may not ask while one is open. None left open: `run.py release <unit>`, then go on to step 6. Otherwise: `run.py redo <unit> <sha> held`.
6. Covered: `run.py go <unit> <sha>`. If it refuses with `unit '<unit>' is held:`, handle it as step 5. If it refuses because another unit holds the slot or is first in the queue, or (serial mode) because the unit `merges after` a unit not yet merged: `run.py queue <unit> <sha>`. For `merges after`, `queue` works for the slot holder too: it gives up the slot and is queued.
7. Not covered: `run.py redo <unit> <sha> '<reasons>'`, `<reasons>` the JSON's `reasons` joined by `, ` (no `not covered: ` prefix).

Once a `no-worktree-path` or `check-error` is sorted out, send the child one message to ask again.

**Questions to the owner** go in the reply text, with the child's recommendation and yours, and under "Waiting on you" in the tracker. Never use the pop-up question tool: while it waits, no event is handled. The answer arrives as a normal user message.

**Messages** go to a child only for what no file carries: an owner answer, a `BEHIND` sync, a merged part k of N, a dead poll, a request format fix, a merge bar the check failed, a stopped unit that had started, a PR to retarget. Never send one alongside a `go`, `redo` or `open`, or a `stop` to a unit still gated: the child's poll reads the file within a minute. A started unit's `stop` is the one exception, since nothing polls `gates.log` for it any more. Never mention reviews; `redo` reasons say when one is needed. A gated child gets a message only if it is still `[gated]` 5 minutes or more after its gate opened: its gate loop died, so tell it its gate is open.

**Late work in integration mode.** Every card, every unit the user adds, every ORPHAN and every owner-approved fix from an escalation targets `integration/<slug>`, before or after the final gate: its prompt uses the unit prompt's integration-mode changes, its session starts with `source_branch: integration/<slug>`, and a PR opened against `<base>` is retargeted with `gh pr edit <pr> -R <repo> --base integration/<slug>`. The final PR waits until that work lands (`status` lists `final PR #<pr> waits on <units>`), an ORPHAN until you record it merged or closed.

## The merge bar

All of:
- `READY` or `REMIND` for that PR and head, or `run.py check <unit>` printing `READY <pr> <sha>`;
- `branch-review:check --repo <worktree> --commit <sha>` covered on that head, `<worktree>` the unit's worktree;
- no unanswered or queued request from that unit, and in serial mode the slot is free or held by that unit (`run.py status` shows both);
- the unit is not stopped (`run.py status` does not list it `stopped`);
- the unit is not held and every `--after` unit has merged (`run.py status` shows neither `hold <unit>` nor `<unit> … merges after`);
- no approved push is outstanding for that unit (`run.py status` does not list `push approved for <unit>`). The child is about to push a newer commit, so wait for it; a `READY` for its new head follows.
- the run is not in integration mode, or `run.py status` lists no `integration sync in flight` for a unit PR, no `final PR … waits on` for the final PR, and the final PR is not owner-merged (`final merge: owner` in the `integration:` line).
- the run is not in integration mode, or the PR targets `integration/<slug>` (a unit PR) or `<base>` (the final PR): `run.py status` lists no `<unit> PR #<pr> targets …` for it.

The child being idle is not required: it cannot push without a `go`, an outstanding `go` holds the merge, and `--match-head-commit` guards it.

Not met because the check says not covered: send the child one message: its PR head `<sha7>` is not covered (`<reasons>`); fix that and ask to push. Not met because the check errors or the unit has no worktree: tell the user in one line. An unanswered request: answer it first. A queued request, another unit's slot, a hold or an unmerged `--after` unit: do nothing; the unit's turn comes through `NEXT`, its next request or the watcher's next `READY`. An integration sync in flight or a final PR that waits on units: do nothing; the watcher reports `READY` or `REMIND` once it clears. An owner-merged final PR: never merge it. A PR on the wrong base: send its child one message to retarget it, as the `targets` line says.

**Merge:** `gh pr merge <pr> -R <repo> --<method> --match-head-commit <sha> && gh pr view <pr> -R <repo> --json state --jq .state`, which prints `MERGED`. If it fails because the head moved, do nothing more: the watcher reports the new head. For anything else (approval required, conflicts, branch protection), tell the user.

**After a merge:**
1. If the PR's title says `(part k of N)` with k < N: `run.py merged <unit> <pr> --more`, send the child one message that part k merged and it may start part k+1, and skip to step 4.
2. `run.py merged <unit> <pr>`.
3. Save the PR description with `mkdir -p <run>/prs && gh pr view <pr> -R <repo> --json body --jq .body > <run>/prs/<unit>-<pr>.md`, and read from that file only what `notes.md` needs (and anything the child messaged you about it). Read the app's shared notes folder for files the merged unit wrote (`<unit>-notes.md`). Its path is at the top of `notes.md` (Setup, step 3). If it is not there yet: the app adds it to each child's prompt, so look among your own additional working directories, or else in one child's first prompt (`list_events`, paging back with `before_uuid` to the child's first message), and write it there. Append a section for the unit to `notes.md`: its PRs, and what later units must know that the specs don't say (owner decisions, changed names or ids, new mechanisms, limits found), from either source. `notes.md` stays the one record you keep. Then `run.py open-ready`.
4. Run `run.py status`. Act first on any `<unit> can merge now its --after units merged` line it lists (the "needs the manager" list above). Then reply with the tracker. Send no other message to the merged unit's child.

## The `specs` unit

This session's own PR goes through the same queue. Before each push of its branch, run `/branch-review:review --base origin/<base>` on it to convergence (escalated findings go straight to the user; later runs reuse the stored base). Then handle it as a `REQUEST` for `specs` with this session's own working directory: covered gets `run.py go specs <sha>` or `run.py queue specs <sha>`; once it has the `go` (at once, or after `NEXT specs`), sync with `<base>`, validate, and push, as a child does on `go`. Its merge bar is the same. The rows that message a child apply to this session's own work instead.

## Finishing

When every unit is merged: confirm with `gh` that each PR merged into the base (in integration mode, each unit PR into `integration/<slug>` and the final PR into the base, and then delete the integration branch: `gh api -X DELETE repos/<repo>/git/refs/heads/integration/<slug>`; a 422 `Reference does not exist` means GitHub already deleted it on merge), and check whatever the repository uses to track the work (an epic table, a changelog). Report the merged PRs, decisions recorded along the way, and the follow-ups left (tech debt, deferred items, a release, tracking docs that are out of date). Propose real follow-ups as cards. Offer once to archive the child sessions; archive only on a yes, each by its session id from `notes.md` with `archive_session` (a detached child is not archived with this session).

## Tracker

After setup, after every merge, and whenever something waits on the user, end the reply with this, built from `run.py status`. Name units as `status` lists them, with the title in brackets when there is one (e.g. `column-overrides (8.7)`).

```
Run <run> (<owner/repo>)
- Integration: <branch> into <base> · final merge: <manager|owner> · feature review: <yes|no>
- Slot: <unit> since <HH:MM> | free
- Queue: <unit> · <unit> | empty
- <unit> merged #<pr> · <unit> merged #<pr>
- <unit> PR #<pr> open · <unit> building · <unit> PR #<pr> open, merges after <unit> · <unit> held until it asks again
- <unit> gated on <units>
- Waiting on you: nothing | <what>, holds included except `answer sent:` ones
```

The `Integration:` line appears only in integration mode.

## Red flags

| Thought | Reality |
|---|---|
| "I'll start the next unit when this one merges" | That turn is a background event; the start becomes a card. Start everything now, gated. |
| "I'll wait for the child's note" | Detached children send none, and notes can be held for hours. Act on the watcher's lines, child messages and `run.py status`. |
| "Detaching hides the children; I'll keep them nested" | Their notes cost a turn each and carry nothing you act on. Detach each one once it is recorded. |
| "Merges notify me" | They don't, and passing checks don't either. Only `run.py wait` tells you. |
| "The wait printed its line; I'll restart it later" | Restart it before ending the turn. Without it the run hears nothing. |
| "I'll ask the owner with the question tool" | It blocks every event behind it. Ask in the reply text. |
| "All checks pass, merge" | Also: `branch-review:check` covered on *this* head, and no unanswered request. |
| "The PR is ready but the child is running" | Merge if the bar is met. The child cannot push without a `go`. |
| "The child says its review is clean" | Run `branch-review:check` yourself. |
| "It's only a clean sync, it needs a review" or "it's only a merge from the base, no check needed" | The check decides both: a clean base merge is covered, a conflicting one says `base-conflict`. |
| "The Review notes list findings outside the change, and this repo forbids deferring; refuse the push" | `outside` is not a deferral (`deferred` means the owner chose it), and the check decides the push and the merge. Where the repo forbids deferring, the review escalates outside findings and the check says `escalated`; relay them like any escalation. If such a repo's Review notes still list outside findings the check does not count as escalated, give them to the owner as a question, and do not hold the push. |
| "The next queued unit should sync first" | The `go` covers it: the child syncs right before it pushes. |
| "I'll append the go to `pushes.log` myself" or "I'll message the go" | `run.py go`; it keeps the slot and the queue. Never a message. |
| "`STUCK … no-push`: yield, then tell the child to read `pushes.log`" | A dead poll is the likely cause. After a yield, that old `go` would push without the slot. Message only, no yield. |
| "`STUCK … no-push` and the child is syncing; yield" | It is acting on the `go`. Yield only when it is at `[waiting]` or `[blocked]`, or gone. |
| "The holder is waiting on the owner; it keeps the slot" | A blocking question or an escalation: `run.py hold`, which frees the slot. It asks again once you forward the answer. |
| "I'll hold this PR until the owner answers" | `run.py hold`, never memory. Only `hold` stops the watcher reporting it `READY`. |
| "I forwarded the answer, so the hold can go" | `release`, then `hold <unit> answer sent: <topic>`. The old head stays unmergeable until the child asks again. |
| "8.6 conflicts with 8.7, add a prereq" | `--after` if it's only merge order. A prerequisite keeps the unit gated until the other merges. |
| "The child says nothing waits on me; I'll confirm" | No reply. Apply what it asks and spend no send. |
| "Auto-fix woke the child; it can push the fix" | It asks first, every time. |
| "Part 1 merged, open the dependents' gates" | Not until part N: `merged --more` keeps the unit open. |
| "I'll let the child know its PR merged" | It doesn't need to know, except a non-final part. Every message spends the 10-send budget. |
| "The child gave a status update; I'll summarize it for the user" | One line at most, nothing about progress. |
| "The next prompt should mention what 5-3 changed" | Prompts are written up front. Put it in `notes.md` before opening the gate. |
| "The final PR is ready; merge it" | Only when the owner chose `manager`. `FINAL-READY` is never merged: the owner merges it. |
| "I'll sync main into the integration branch myself" | The integration child does it. The manager writes no code. |
