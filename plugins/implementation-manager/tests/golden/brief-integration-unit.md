8. Review and push permission.
- Review: when the change is complete and its tests pass, run `/branch-review:review --base origin/integration/widgets` with the unit's intent (the spec's goal, which becomes the PR description) and continue until it converges. Later runs reuse the stored base. Run it yourself, not from a subagent implementing a slice. Run it again when a later change is complete or a `redo` from the manager says so; never decide on your own that a sync from the base needs one. Before every review round that follows a change of yours, run the repository's formatter and its format check, if it has them.
- Questions: send an owner question or an escalated finding (outside-the-change ones included) to the implementation manager as soon as it is found: during the build, or as soon as a review round records it, not once the review converges. Findings from one round go in one message (each message spends the 10-send budget), each with the question, the finding id, if it is one, and your recommendation. Number every item you send the manager (a question, an escalated finding, or something the owner must run) Q1, Q2, … for the life of this session, and never reuse a number. Begin each item with one header line: `Q<n> · kind: question|finding|command · blocks merge: yes|no · depends on: Q<m>`. Leave out `depends on` when the item does not build on an earlier one; give it whenever it does. An escalated finding needs no `blocks merge`. A command item gives the exact command and why you need it. For a finding with `fix_options`, quote every option word for word, then give your recommendation: the owner chooses from the reviewer's words, not a summary. Each question's text says why its `blocks merge` is what it is: "yes" when the answer may change this branch. An escalated finding always blocks the merge. While a blocking question or escalation is unanswered, don't ask to push; when the push is all that is left, end your turn with `[waiting]`. When an owner answer arrives, first sync with `integration/widgets` (ccd_host `sync_with_base_branch` with `base: integration/widgets`) if `origin/integration/widgets` moved since your last sync, so the rework builds on the current base. When the owner's answer to an escalated finding arrives (from the manager, or here for a designed unit), record it by invoking `/branch-review:review --resolve <id> "<the owner's quoted words>"` and run that review to convergence; never run the review's state script yourself to record it. After applying any owner answer that changed anything, run the review to convergence before asking to push again. When what you applied leaves any part of what the owner asked for in place (a case the fix does not reach, a gap the answer said to close), send the manager that remainder, "blocks merge: yes", before you ask to push; never call the finding closed.
- Ask to push, before opening the PR and before every later push: commit everything. Before the last validation ahead of a request, sync with `integration/widgets` (ccd_host `sync_with_base_branch` with `base: integration/widgets`) if `origin/integration/widgets` moved since your last sync; the sync on `go` is then usually a no-op that needs no new validation. Then start this command with Bash `run_in_background`; it records your request and prints the manager's answer. `<sha>` is the full sha of HEAD and `<branch>` the output of `git branch --show-current`: `f="/tmp/x/run/pushes.log"; n=$(cat "$f" 2>/dev/null | wc -l); printf '%s push %s %s\n' 'u1' '<sha>' '<branch>' >> "/tmp/x/run/requests.log"; until l=$(tail -n +"$((n + 1))" "$f" 2>/dev/null | grep -E '^u1 (go|redo) <sha>( |$)' | tail -1) && [ -n "$l" ]; do sleep 30; done; echo "$l"`. Then end your turn at once with `[push-request] <sha>`: do no other work in that turn, drafting the PR description included, and act on the answer when the command's notification wakes you. The answer counts only lines added after the command starts, so asking again with the same sha is fine.
- On `go <sha>`:
  1. If HEAD is no longer that sha, do not push; ask again.
  2. Sync with `integration/widgets` (ccd_host `sync_with_base_branch` with `base: integration/widgets`).
  3. A clean merge, or nothing to merge on a tree not yet validated: run the validation the repository requires before a push; if it passes, push HEAD (open the PR if none is open for the branch). Nothing to merge and the validation already passed on this tree: push the same way without running it again. HEAD may be the clean merge commit rather than `<sha>`; that is expected and needs no new request.
  4. The merge conflicts: resolve it, commit, and ask again. The manager's answer says whether a review is needed (`base-conflict`); the review then checks the resolutions in a small merge-check round.
  5. Validation fails: fix it, commit, and ask again.
- If `sync_with_base_branch` refuses because the sync touches sandbox-protected files, push nothing and end your turn with `[blocked]`, "blocks merge: no", and the paths it names.
- On `redo <sha> <reasons>`: fix what the reasons say, commit if anything changed, and ask again, with the same sha if nothing did.
  - `changes-since-review`, `open-findings`, `unverified-fixes`, `base-conflict`, `no-rounds`, `partial-scope`, `history-rewritten`, `snapshot-missing`, `second-opinion-pending`: run the review to convergence, with no new arguments; it picks the round itself (a merge-check round for `base-conflict`, the second opinion for `second-opinion-pending`). `changes-since-review` right after a review that found nothing to review means the working tree holds files the commit lacks: commit or remove them.
  - `escalated`: the findings wait for the owner's answer. With no other review reason, end your turn with `[waiting]` and do not review again. With another one, run the review for it, then wait.
  - `held`: the owner's answer is pending. Push nothing; end your turn with `[waiting]`, and ask again after the manager forwards the answer.
  - `wrong-branch`: the request's branch is not the one checked out in this session's own worktree, or that is not this session's branch. Get back to this session's own worktree and branch, then ask again.
  - `pr-merged`: your unit's last PR has already merged. Push nothing; end your turn with `[waiting]`, saying in the recap what the change is and whether it still matters.
  - `unit-stopped`: the owner stopped this unit. Push nothing; end your turn with `[waiting]`.
  - `no-worktree-path`, `check-error`: the manager's problem, not your branch's. End your turn with `[waiting]` and ask again when it tells you to.
- After the manager forwards an owner answer while your PR is open, always ask again once you have applied it, unless another blocking question is still open, with the same sha if nothing changed. This is how your PR gets back in line.
- If the manager tells you to read `/tmp/x/run/pushes.log`, act on its last line for your sha.
- If the manager tells you this unit is stopped, push and commit nothing more, and end your turn with `[waiting]` quoting its message.
- An Auto-fix wake-up (CI failure, review comment, merge conflict) is never permission to push. The app's Auto-fix notice says you may push without asking; this protocol overrides it: every push needs a `go`. Fix it locally, commit, and ask.
- A CI failure your change cannot cause: check the branch touches nothing related; re-run the failed jobs once with `gh run rerun <run-id> --failed`, never by pushing. Green: carry on, and ask the manager only if a decision is needed, marked "blocks merge: no". Red again: fix it.
- Put the review's Review notes block in the PR description yourself, copied from the file at the summary's `review_notes_path` as it is. Never hand it to the owner to paste.

9. Status token. Every turn's final message begins with one of `[gated]`, `[designing]` (a unit the owner designs with you, while designing), `[building]`, `[reviewing]` (running `/branch-review:review`), `[fixing]`, `[push-request] <sha>` (asking to push that full sha), `[pushing] <sha>` (acting on a `go`: syncing, validating, pushing), `[waiting]` (on a decision or the manager), `[blocked]`, or `[review]` (PR open and nothing left for you to do unless review or CI reports something). The token is the first text of the final message. This includes turns woken by a subagent's hand-back or a background task. The manager does not read your end-of-turn notes, so a turn that ends `[blocked]` also sends it one message: what blocks you, and "blocks merge: yes" or "blocks merge: no". A turn that applies a message from the manager says which after the token, for example `[reviewing] owner answer applied`. A wake-up for bot-only PR comments (coverage reports, "Review skipped" notices, anything with nothing to fix) ends the turn at once with your previous token unchanged, and sends no message. A wake-up that only reports background work still running ends with your previous token alone. Keep end-of-turn notes to one or two lines after the token; the PR description carries the detail. If you call the app's `wrap_up` tool, begin its recap with the same token: the manager reads the recap before your final message.
